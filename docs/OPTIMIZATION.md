# 业务落地优化建议

以下建议基于当前 Demo 的实际表现（生成 30-60 秒、执行 60-100 秒、JSON 文件存储、Redis 缓存、单模型调用），按「解决什么问题 → 怎么优化 → 预期收益」组织，并给出优先级。

> 更新：P0 六项已在本 Demo 中落地（见下方「已落地」标注），可作为后续迭代基础。

> 风险视角：实际部署时的完整风险清单见 [RISKS.md](RISKS.md)。

## 一、生成环节：质量与成本

### 1. 需求澄清与追问（P0 · 已落地）

- 问题：用户一句话需求往往信息不足（数据口径、输入来源、输出形式都模糊），一次生成容易跑题或返工。
- 方案：生成前增加意图识别与澄清：识别岗位类型、业务域、数据源；必要时追问 1-3 个问题（如“数据来自哪里”“按周还是按月复盘”“面向谁汇报”）。已实现：规则预判（需求明确直接生成）+ LLM 追问。
- 收益：减少无效 LLM 调用，提升首轮可用率。

### 2. 企业经验库 + RAG（P1）

- 问题：目前 Skill 完全依赖模型记忆，企业沉淀的经验没有进入生成过程。
- 方案：建立企业岗位经验知识库（历史 Skill、优秀复盘报告、指标口径、话术模板），生成时检索相似经验作为 few-shot 上下文注入。
- 收益：生成结果更贴合企业私有口径，减少“通用化、跑题”问题。

### 3. 生成后语义校验（P0 · 已落地）

- 问题：当前只有 Schema 校验（字段、类型），没有校验“内容是否真的符合需求”（实测曾生成与需求无关的 Skill）。
- 方案：增加语义一致性检查：名称与需求主题相关度、输入字段可采集性、分析流程可执行性；校验失败自动重生成或交给人工确认。已实现：规则校验（字段/步骤/占位符）+ 主题一致性，失败自动重试。
- 收益：拦截错误 Skill，守住企业使用底线。

### 4. 模型路由与分层（P1）

- 问题：所有请求都用同一个强模型，成本和延迟偏高。
- 方案：按需求复杂度路由：简单需求用轻量模型，复杂需求用强模型；支持模型降级（强模型超时/失败自动切换）。
- 收益：平均成本下降 30%-50%，延迟更稳定。

## 二、执行环节：可靠性与可解释性

### 1. 指标口径库（P0 · 已落地）

- 问题：确定性指标目前只覆盖抖音直播场景，其他场景的指标由 LLM 现场计算，存在口径漂移和幻觉风险。
- 方案：建立“指标字典”：每个指标绑定标准公式、字段映射、单位和校验规则；规则引擎优先计算，LLM 只负责解读和归因。已实现：覆盖抖音直播、电商、销售、用户增长、零售门店五类共 27 个指标，按字段自动匹配计算。
- 收益：结果可复核、口径统一，企业才敢让 AI 员工直接产出报告。

### 2. 结果溯源与一致性检查（P1）

- 问题：报告里的数字可能来自模型推算，无法追溯。
- 方案：输出时附带数据来源（字段名 + 公式 + 原始值）；增加数字一致性校验（报告中关键数字必须能在输入数据中找到依据）。
- 收益：结论可解释、可追责，增强信任。

### 3. 任务状态机与异步化（P1 · 已落地）

- 问题：当前执行是同步流式，用户刷新即中断；长任务体验受限。
- 方案：引入任务队列与状态机（排队 → 运行 → 完成/失败），支持重试、取消、断点续跑，完成后推送通知。已实现：后台任务线程 + 任务表落库 + SSE 订阅，刷新/断线可恢复进度，失败可重试；生产可替换为 Celery/RQ 等正式队列。
- 收益：支持批量分析和长时间任务，刷新不丢进度。

## 三、缓存与性能

### 1. 三级缓存（P1）

- 问题：目前只有 Redis 单层缓存，且只缓存“需求 → Skill 配置”。
- 方案：
  - L1 进程内缓存（毫秒级热点命中）
  - L2 Redis 缓存（跨实例共享）
  - 按需求热度动态调整 TTL
- 收益：进一步降低平均延迟与 LLM 成本。

### 2. 语义缓存（P2）

- 问题：文本完全一致才命中，相似需求（换个说法）仍会重复生成。
- 方案：需求 embedding + 向量检索，相似度超过阈值且经人工确认后复用；不同结果分别缓存。
- 收益：提高缓存命中率，但需谨慎处理“看似相似实则不同”的边界。

### 3. 执行结果缓存（P1）

- 问题：同一 Skill + 同一份数据会被重复分析。
- 方案：以 Skill ID + 输入数据哈希为键缓存执行结果，数据未变直接返回。
- 收益：重复查询零成本，适合周报、月报等固定数据场景。

## 四、数据与资产管理

### 1. 数据库化与版本管理（P0 · 已落地）

- 问题：JSON 文件存储无法支撑并发、检索和审计。
- 方案：迁移到 PostgreSQL/MySQL，Skill 增加状态流（草稿 → 审核 → 已发布 → 下线）、版本号、变更记录。已实现：SQLite 存储 + 版本历史（重复保存自动升版本，历史版本可查）；生产可平滑替换为 PostgreSQL。
- 收益：多人协作、权限控制、灰度发布成为可能。

### 2. 资产血缘（P1）

- 问题：Skill 与数据源、模型版本、输出报告的关联关系没有记录。
- 方案：记录血缘：Skill → 输入数据 → 模型版本 → 输出报告；支持审计追溯。
- 收益：满足企业合规要求，问题定位快。

### 3. 输入数据质量门禁（P1）

- 问题：用户粘贴的数据可能缺字段、类型错误、数值异常。
- 方案：执行前做数据校验（Schema + 业务规则 + 异常值检测），质量不达标先提示修复。
- 收益：避免“垃圾进垃圾出”，提升结果可信度。

## 五、评估与反馈闭环

### 1. 离线评估集（P0）

- 问题：无法证明一个 Skill“好不好”。
- 方案：每个 Skill 配置一组输入样例 + 预期关键指标/结论，CI 自动跑分（指标正确率、结论方向、格式合规）。
- 收益：发版前有客观门槛，防止劣质 Skill 上线。

### 2. 在线反馈闭环（P1）

- 问题：结果对错没有用户反馈回路。
- 方案：点赞/点踩、采纳率、人工修改率；错误反馈自动进入修正队列，驱动 Skill 迭代。
- 收益：Skill 越用越准，形成数据飞轮。

### 3. Skill 有效度指标（P1）

- 问题：缺少衡量 Skill 业务价值的指标。
- 方案：跟踪使用率、执行成功率、报告采纳率、节省工时等。
- 收益：让平台投入可量化，便于向管理层汇报。

## 六、平台工程

### 1. 部署与可观测性（P0 · 已落地）

- 问题：当前单机直跑，无监控。
- 方案：Docker 化 + CI/CD；监控 LLM 延迟/失败率、缓存命中率、token 成本、接口错误率；日志与告警体系。已实现：Dockerfile + docker-compose（web + redis）、请求耗时日志、`/api/stats` 统计接口。
- 收益：稳定运维，成本透明。

### 2. 安全与合规（P0 · 部分落地）

- 问题：API Key 在 .env 明文、无权限体系、无脱敏。
- 方案：密钥托管（KMS/密钥服务）、多租户权限隔离、敏感数据脱敏、Prompt 注入防护、输出内容合规审查。已实现：输入长度限制、Prompt 注入防护、审计日志（需求哈希）；KMS 与多租户为生产环境待办。
- 收益：满足企业安全与合规要求，才能进生产。

## 七、优先级速查

| 优先级 | 建议 | 理由 |
|--------|------|------|
| P0 | 需求澄清、生成后语义校验、指标口径库、数据库化、部署可观测、安全合规 | 不做这些无法支撑企业真实使用 |
| P1 | 企业经验库 RAG、模型路由、执行结果缓存、输入数据校验、离线评估集、反馈闭环 | 显著提升质量、成本与体验 |
| P2 | 语义缓存、技能市场/模板库、多租户商业化 | 锦上添花，业务规模上来后再做 |
